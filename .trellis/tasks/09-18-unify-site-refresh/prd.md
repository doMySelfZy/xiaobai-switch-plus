# 统一站点模型与余额刷新并修复全局刷新

## Goal

让站点模型列表与余额状态使用同一套自动刷新节奏，减少两套刷新逻辑带来的状态不一致；站点列表的全局刷新一次完成所有启用站点的模型与余额刷新，并修复当前全局刷新拿不到模型、进入站点详情手动刷新却能成功的问题。

## Background

- `src/pages/SitesPage.tsx:91-114` 当前只对当前选中且启用的站点按 30 秒轮询余额，模型没有对应的自动刷新任务。
- `src/pages/FloatingWindow.tsx:283-291` 当前悬浮窗按 `floatingWindow.autoRefreshMinutes` 单独定时调用 `refresh_sites_quota`，只刷新余额。
- `src/pages/SitesPage.tsx:236-285` 当前站点列表全局按钮只并行调用 `fetchModels`，不刷新余额；按钮只统计模型调用是否成功。
- `src/stores/siteStore.ts:321-385` `fetchModels` 会从 store 读取站点当前 active API key，调用 `fetch_site_models`，空结果再回退 `list_site_models`，成功后写入 `modelsBySite`，失败会清空该站点模型缓存。
- `src/stores/siteStore.ts:423-506` `probeQuota` 负责单站点余额缓存、TTL 与 in-flight 去重；`src-tauri/src/commands/floating.rs:73-121` 的 `refresh_sites_quota` 负责后端并发刷新所有启用站点余额并返回汇总，但不会刷新模型。
- `src/pages/SitesPage.tsx:153-161` 进入/切换站点时使用 `listModels` 读取该站点模型缓存，因此手动详情刷新与列表全局刷新走的是不同 UI 入口，但底层都应落到同一 `fetchModels`。
- `src/floating.tsx:13-29` 与主窗口是独立 webview；两者不能共享 zustand 内存状态。余额目前通过 Rust 进程内 `QUOTA_CACHE` 共享，模型结果通过数据库共享。
- 近期提交 `7cbe67d` 新增了全局模型刷新按钮；当前实现未覆盖模型+余额统一刷新，也没有覆盖全局刷新失败场景的回归测试。
- ModelScope 官方 OpenAPI 提供 `GET https://modelscope.cn/openapi/v1/magicubes/balance`，Bearer Access Token 可查询魔粒账户余额（`total_balance`、`available_balance`、`frozen_amount`）；这不是 API-Inference 免费模型的剩余调用次数/免费 token 配额。官方资料未确认稳定的免费额度查询 endpoint，配额会动态调整，因此本任务不把免费调用次数作为可用余额接入。

## Requirements

### R1. 统一自动刷新任务

- 模型与余额自动刷新使用一个定时任务和同一个刷新入口，不再分别维护模型定时器与余额定时器。
- 唯一调度器挂在主窗口应用级常驻组件（`AppInner`），读取现有 `floatingWindow.autoRefreshMinutes` 间隔；主窗口隐藏到托盘或用户切换页面时任务仍保持运行。
- 一次自动刷新针对所有启用站点刷新模型与余额；单站点失败不能阻断其他站点，刷新结束后保留可观察的成功/失败状态。
- 自动刷新结果通过共享 store 更新主窗口模型/余额状态；通过 Rust 后端缓存与刷新事件让独立悬浮窗读取同一轮余额结果。
- 配置刷新间隔变化后，调度器无需重启即可使用新间隔；不能再由站点页或悬浮窗各自创建重复定时器。

### R2. 站点列表全局刷新

- 点击站点列表全局刷新时，对所有启用站点同时执行模型刷新和余额刷新；停用站点不发请求。
- 全局刷新与自动刷新复用同一个 store 刷新入口和同一个底层模型获取函数，使用刷新开始时每站点的 active API key 快照，避免页面状态或密钥切换造成请求错配。
- 全局刷新应刷新站点列表中的模型可用性指示与余额摘要，并在全部成功、部分失败、全部失败时给出正确提示；不能因单个站点失败导致其他站点结果丢失。
- 刷新进行中应防止重复触发，并分别保持各站点已有模型/余额数据显示，直到新结果成功或明确进入错误态。

### R3. 修复全局刷新模型获取 bug

- 覆盖当前“列表全局刷新获取不到模型、进入站点详情手动刷新可以获取”的回归场景。
- 排查并修复全局批量调用中的站点/API key 快照、并发状态写回、错误处理或调用契约问题，不能通过绕过详情刷新逻辑另写一套模型抓取逻辑。
- 同一站点的全局刷新和详情手动刷新必须经过相同的 active key 解析、`fetch_site_models` 调用和空结果回退逻辑。

### R4. 兼容与提示

- 保留现有单站点手动模型刷新、单站点余额刷新、悬浮窗缓存展示和 TTL/in-flight 去重语义，统一入口需要强制网络刷新时只对统一刷新调用使用明确的 `force` 选项。
- 所有新增或修改的用户可见文案继续走中英文 i18n。
- 不改变现有刷新间隔的单位、默认值与设置位置。

## Acceptance Criteria

- [ ] 站点列表全局刷新一次点击后，每个启用站点都产生一次模型刷新和一次余额刷新；停用站点不产生请求。
- [ ] 全局刷新成功后，模型列表、模型可用性指示和余额摘要都更新；部分站点失败时，成功站点结果仍保留且提示统计准确。
- [ ] 对同一站点，列表全局刷新与详情手动刷新使用相同 active API key，并能得到相同模型结果；覆盖原 bug 回归测试。
- [ ] 自动刷新只有一个定时任务/入口，同时更新模型和余额；配置的刷新间隔变化后无需重启即可生效。
- [ ] 主窗口切换页面、隐藏到托盘或悬浮窗独立显示时，不会创建第二个刷新定时器；悬浮窗能读到统一刷新后的余额缓存。
- [ ] 不可见页面、停用站点和重复点击不会产生额外刷新请求；已有的 in-flight 去重仍有效。
- [ ] 前端相关测试、类型检查与 Rust 测试通过。

## Out of Scope

- 不改变模型协议探测、余额接口探测、站点数据结构或数据库协议。
- 不新增独立的刷新间隔配置，不改变现有刷新间隔的单位与默认值。
- 不重做站点列表或悬浮窗视觉布局。
- 不要求悬浮窗获得主窗口 zustand 状态；跨窗口同步继续通过后端缓存/事件完成。
